# snowtest 5.2.0 — Release Notes

**Release date:** unreleased; this note grows as
`feat/5.2.0-coverage-and-fidelity` lands.

No wire format or storage format has changed yet. 5.2.0 is about what a stub has
to be able to prove about itself: that its dbt suite covers what the design
document used to claim by hand, that a deployment checks the instance it just
started, and that the stage path runs in both directions.

## What changed

### The dbt suite covers what was only checked by hand

The design document listed `transient`, `copy_grants`, `cluster_by`,
`automatic_clustering`, the `append` and `delete+insert` incremental strategies,
`contract: enforced`, both snapshot strategies, `dbt source freshness`,
`dbt docs generate` and `dbt run-operation` as verified by hand on an older dbt
pin — a claim the suite could not reproduce. All of it now runs in
`npm run test:dbt`, on the pair pinned in `versions.json`.

Supporting that needed `tests/dbt/fixture.py`: it owns the raw tables the
snapshots and the freshness check read, changes one row between the two snapshot
runs so a second version is recorded, and ages every row so the stale check has
something to fail on. It drops the append ledger and both snapshot tables before
the first run, so a suite re-run on an instance it did not create starts from its
own baseline instead of the previous run's rows — verified by running the suite
twice against one borrowed server.

Two of the new steps exist because they can go quietly wrong. The stale-source
step is *expected* to fail, through a dedicated `expect_failure` helper, so a
freshness check that stops biting turns the suite red rather than green. And
`run-operation` is given the row count it must find, so the macro raises instead
of merely running.

The suite went from 8 steps to 17, and from 57s to 72s on the same machine.

### `redeploy` verifies the instance it started

`./setup.py redeploy` rebuilt, replaced, reseeded, and then printed a summary
whether or not the thing it started could answer a client. It now posts to the
instance's own self test after seeding and, before printing that summary, fails
with the name of every check that did not pass.

- `--no-verify` skips the step. The self test writes to a scratch database it
  drops again, but it leaves two rows in
  `SNOWFLAKE.ACCOUNT_USAGE.MODEL_FIDELITY` under `model.snowtest_selfcheck.*`,
  which is why the opt-out exists.
- A run already in flight (HTTP 409), a report with no checks in it, or an
  instance that cannot be reached all count as failures: "could not check" must
  never read as "it is fine".
- The verdict is read from the check list rather than from the report's summary
  fields, so the checks that are printed and the checks that are judged cannot
  disagree.

### `COPY INTO @stage` unloads

The reverse direction used to be refused outright: the statement parser only knew
the load form, so `COPY INTO @stage/…` came back as a Snowflake error. It now
unloads, into the same local-filesystem stage `PUT` and `GET` use, by handing the
file to DuckDB's `COPY … TO`.

- `FROM (query)` or `FROM table`. The query is translated like any other
  statement, so what it approximates is reported against the model that sent it.
- CSV and Parquet, with `COMPRESSION` (`AUTO` is gzip for CSV and snappy for
  Parquet), `HEADER`, `FIELD_DELIMITER`, `FIELD_OPTIONALLY_ENCLOSED_BY`,
  `NULL_IF`, `SINGLE` and `OVERWRITE`. CSV is unquoted by default, as Snowflake's
  `NONE` is: a value holding the delimiter is written raw rather than quoted.
- One row of `rows_unloaded`, `input_bytes` and `output_bytes`, as Snowflake
  returns. A stub cannot know the pre-compression stream size, so both byte
  counters report the bytes written.
- The file is named the way Snowflake names it: `data_0_0_0.csv.gz` for a
  parallel unload, `data` under `SINGLE = TRUE`, or whatever the path names.
  There is one file, not one per warehouse thread.
- A zero-row unload writes no file. `PARTITION BY`, `INCLUDE_QUERY_ID` and
  unloading as JSON are refused by name rather than returning something that
  looks like an answer.

### Integer division has a verdict

`1/3` has returned a double (`0.3333333333333333`) where Snowflake returns
`0.333333` since the DuckDB engine landed, and 5.0.1 recorded it as a gap that was
neither fixed nor reported: an operator has no rewrite to hang a note on.

It is reported now, as `integer division`, whenever both operands are integer
literals. That is deliberately narrow. `1/3` is the case whose types this pass can
know without the catalog; `AMOUNT/2` stays silent rather than guessing at a
column's type, and `1.5/2` already divides in double. Under `strict` a model that
divides two literals is refused, like any other approximation.

Still not fixed: the value. DuckDB divides in double precision, and a rewrite that
forced six decimal places would change what the operator returns for every
caller — a semantic change no note makes safe.

## Upgrading

Nothing to do for configuration: no setting, schema or wire format changed, and
`package.json`, `package-lock.json` and the `compose.yaml` image-tag fallback are
still the only places that name the version.

One behaviour change, and only under `strict`: a model that divides two integer
literals (`1/3`) is refused now, because `integer division` is a reported
approximation. It used to run and quietly return a double (`0.3333333333333333`
instead of Snowflake's `0.333333`). The default mode, `report`, still runs it and
records the verdict, so a setup that never turned strict on sees no difference.
If you do run `strict` and a model divides two literals, the refusal names
`integer division`, and `report` is the way past it if you would rather keep the
model running.
