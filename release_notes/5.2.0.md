# snowtest 5.2.0 — Release Notes

**Release date:** unreleased; this note grows as
`feat/5.2.0-coverage-and-fidelity` lands.

No wire format, storage or client-visible behaviour has changed so far. 5.2.0 is
about the two things a stub has to be able to prove about itself: that its dbt
suite covers what the design document used to claim by hand, and that a
deployment checks the instance it just started.

## What changed

### The dbt suite covers what was only checked by hand

The design document listed `transient`, `copy_grants`, `cluster_by`,
`automatic_clustering`, the `append` and `delete+insert` incremental strategies,
`contract: enforced`, both snapshot strategies, `dbt source freshness`,
`dbt docs generate` and `dbt run-operation` as verified by hand on an older dbt
pin — a claim the suite could not reproduce. All of it now runs in
`npm run test:dbt`, on the pair pinned in `versions.json`.

Supporting that needed `tests/dbt/fixture.py`: it owns the raw tables the
snapshots and the freshness check read, changes one row between the two snapshot
runs so a second version is recorded, and ages every row so the stale check has
something to fail on. It drops the append ledger and both snapshot tables before
the first run, so a suite re-run on an instance it did not create starts from its
own baseline instead of the previous run's rows — verified by running the suite
twice against one borrowed server.

Two of the new steps exist because they can go quietly wrong. The stale-source
step is *expected* to fail, through a dedicated `expect_failure` helper, so a
freshness check that stops biting turns the suite red rather than green. And
`run-operation` is given the row count it must find, so the macro raises instead
of merely running.

The suite went from 8 steps to 17, and from 57s to 72s on the same machine.

### `redeploy` verifies the instance it started

`./setup.py redeploy` rebuilt, replaced, reseeded, and then printed a summary
whether or not the thing it started could answer a client. It now posts to the
instance's own self test after seeding and, before printing that summary, fails
with the name of every check that did not pass.

- `--no-verify` skips the step. The self test writes to a scratch database it
  drops again, but it leaves two rows in
  `SNOWFLAKE.ACCOUNT_USAGE.MODEL_FIDELITY` under `model.snowtest_selfcheck.*`,
  which is why the opt-out exists.
- A run already in flight (HTTP 409), a report with no checks in it, or an
  instance that cannot be reached all count as failures: "could not check" must
  never read as "it is fine".
- The verdict is read from the check list rather than from the report's summary
  fields, so the checks that are printed and the checks that are judged cannot
  disagree.

## Upgrading

Nothing to do. No configuration, schema or wire change. `package.json`,
`package-lock.json` and the `compose.yaml` image-tag fallback are the only places
that name the version, and they all say 5.2.0.
