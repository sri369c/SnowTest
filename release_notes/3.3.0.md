# snowtest 3.3.0 — Release Notes

**Release date:** 2026-11-15

A minor release, because behaviour changed rather than only the packaging:
`BEGIN`, `COMMIT` and `ROLLBACK` are real, a request holding several statements
runs all of them, and the clock can be frozen. The storage layout and the
configuration format are unchanged.

## What changed

### Transactions roll back

`BEGIN`, `COMMIT` and `ROLLBACK` used to be accepted and ignored — DuckDB
autocommits, so there was nothing to do. The consequence was worse than it looked.
A client that opened a transaction, wrote rows and rolled back kept the rows, so a
test asserting "the failed load left nothing behind" passed with the data still
there.

They are real transactions on the session's own DuckDB connection now:

- a rollback discards everything the transaction wrote;
- a statement that fails inside a transaction aborts it, and the client has to roll
  back before it can run anything else, as Snowflake requires;
- a logout or an idle expiry closes the connection, which rolls back whatever was
  still open.

Two details are worth knowing. DuckDB has no `SAVEPOINT`, so the router's own
internal transactions (the typed `CREATE TABLE … AS SELECT`, `ALTER TABLE …
RENAME TO`, `SWAP WITH`) join an open client transaction instead of nesting inside
it, and no longer commit behind the client's back. And existence checks read the
session's connection while a transaction is open, because the admin connection that
serves `DESCRIBE` and `SHOW` only sees committed state; without that, a table
created inside a transaction looked like it did not exist.

Account objects are the exception: `CREATE DATABASE`, `CREATE SCHEMA`,
`CREATE WAREHOUSE`, `CREATE ROLE` and `CREATE STAGE` are not rolled back by a
transaction.

### A request may hold several statements

A request is split on `;` and every statement is routed and run in turn. Separators
inside string literals, quoted identifiers, comments and `$$…$$` bodies do not
split. The driver protocol answers with the last statement's result, which is what
a script's caller reads; the SQL API returns one result object per statement.

`MULTI_STATEMENT_COUNT` is enforced when the client sets it: a count that does not
match the request fails the whole request. It is not enforced from the default,
because the default of 1 would reject every script.

### `SNOWTEST_CLOCK`: a clock you can freeze

`SNOWTEST_CLOCK` freezes or shifts the time the server reports:

```bash
# container started by setup.py: the host environment is not forwarded, so pass
# it explicitly. --recreate is what makes an existing container pick up the value.
./setup.py up --recreate --env SNOWTEST_CLOCK=2026-01-31T09:00:00Z   # frozen
./setup.py up --recreate --env SNOWTEST_CLOCK=+30m                   # host clock, +30 minutes

# compose: exported on the host, because compose.yaml forwards it
SNOWTEST_CLOCK=+30m podman compose up -d

# from source
SNOWTEST_CLOCK=+30m npm start
```

`setup.py` forwards only what it is told to: `SNOWTEST_PORT`, `SNOWTEST_STAGE_ROOT`
and `SNOWTEST_DATA_DIR` itself, plus `--env KEY=VALUE`, `--public-key` and
`--users`. A variable exported in the shell does not reach the container.

`CURRENT_TIMESTAMP`, `LOCALTIMESTAMP`, `CURRENT_TIME`, `LOCALTIME`, `CURRENT_DATE`,
`SYSDATE` and `GETDATE`, bare or with `()`, follow it, precision variants included.
An offset is resolved per statement, so time still moves during a long run.

### `--port 0` picks a free port

For running an instance inside a test process rather than as a container: `--port 0`
binds a free port, and the startup line prints the one that was chosen.

### `CREATE TABLE … CLONE`

`CREATE [OR REPLACE] [TRANSIENT] TABLE [IF NOT EXISTS] t CLONE src` copies the
source's column definitions (`NOT NULL` included) and its rows into a new table.

It is a copy, not Snowflake's zero-copy clone: storage and time grow with the
source, and the two tables are independent from then on. `AT` and `BEFORE`, and
`CREATE DATABASE | SCHEMA … CLONE`, are refused with an error instead of being
approximated.

### `/operations` says when each support arrived

Every table on `/operations` gained a **Since** column: the release that gave the
row the status it shows today. The values were read from each release's own table,
so a row promoted from partial to supported carries the version of the promotion,
not of the row's first appearance. The page's lede says exactly that.

## Changes to existing surfaces

| Surface | Change |
|---|---|
| `BEGIN` / `START TRANSACTION` / `COMMIT` / `ROLLBACK` | Real transactions on the session's connection; a failed statement aborts until `ROLLBACK` |
| `POST /queries/v1/query-request` | A request holding several statements runs all of them and answers with the last result |
| `POST /api/v2/statements` | Same, and `data` holds one result object per statement |
| `MULTI_STATEMENT_COUNT` | Honoured when the client sets it |
| `CREATE TABLE … CLONE …` | Works, as a full copy; `AT`/`BEFORE` and database/schema clones are refused |
| — (`SNOWTEST_CLOCK`) | New: freezes or shifts the emulated clock |
| `--port` / `SNOWTEST_PORT` | `0` binds a free port |
| `GET /operations` | New **Since** column on every table |
| Image tag | `snowtest:3.3.0`, read from `package.json`; `compose.yaml`'s fallback bumped with it |

## Upgrading

```bash
./setup.py redeploy          # rebuilds as snowtest:3.3.0, keeps the data volume
# or by hand
podman build --layers=false --format docker -t snowtest:3.3.0 .
```

`redeploy` clears staged files before bringing the new image up; `--no-seed-examples`
skips the reseed. No configuration or schema change is needed.

Worth checking on the client side: transactions that used to be ignored are now
real, so a session that issues `BEGIN` and never commits has that work rolled back
when it ends.

## Known limitations

- No time travel: `CLONE … AT/BEFORE` and `CREATE DATABASE | SCHEMA … CLONE` are
  refused.
- `CLONE` is a full copy, not zero-copy.
- Account-level DDL is not part of a transaction.
- `LATERAL FLATTEN`, streams, tasks, dynamic tables and RBAC are unchanged: still
  not supported.
- `MULTI_STATEMENT_COUNT` is only enforced when the client sets it, so a client
  that never sets it can still send a script whose statement count Snowflake would
  reject.
- The SQL API's multi-statement body follows the documented array shape, but the
  connector suite only sends single statements, so that shape is covered by unit
  tests rather than by a real client.
- The driver's `execute_async` + `get_results_from_sfqid` polling is unchanged.
