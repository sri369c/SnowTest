# snowtest 4.0.0 — Release Notes

**Release date:** 2026-11-15

A major release because three surfaces changed what they answer rather than only
how they answer: `GRANT` and `REVOKE` used to fail, `LATERAL FLATTEN` had no
translation, and `DESCRIBE STAGE` / `DESCRIBE FILE FORMAT` answered "Not
implemented.". Nothing else in the storage layout, the configuration or the wire
protocol moved.

## What changed

### Access control statements are accepted, and recorded

`GRANT` and `REVOKE` reached DuckDB and died on its parser, because DuckDB has no
privilege grammar. That took out whole dbt projects over a `grants:` block, which
is a strange thing for a stub to refuse: the config never had an effect on a real
account either, until someone looked.

They are recorded now, and can be read back:

- `GRANT <privileges> ON <object> TO ROLE|USER <name> [WITH GRANT OPTION]`
- `GRANT ROLE <a> TO ROLE|USER <b>`
- the matching `REVOKE`s, `GRANT OPTION FOR` and `CASCADE` / `RESTRICT` included
- `SHOW GRANTS`, `SHOW GRANTS TO ROLE|USER`, `SHOW GRANTS OF ROLE`, and
  `SHOW GRANTS ON <object>`, each in the column shape Snowflake gives that variant

Nothing is enforced, and the documentation says so rather than implying RBAC: any
role can still read and write anything, ownership never changes hands, and a grant
on an object that does not exist is accepted. What the recording buys is a `SHOW
GRANTS` that tells the truth about what was asked, instead of an empty list.

A dropped role takes its grants with it, as Snowflake does.

### `LATERAL FLATTEN` works

`FLATTEN` is how Snowflake turns a variant array or object into rows, and it had
no translation at all — the statement failed. It is translated into DuckDB's
`json_each`, which walks the same documents and reports the key, the value and the
path of each element:

```sql
select f.key, f.index, f.value
from docs, lateral flatten(input => docs.body) f
```

The six columns Snowflake documents are all there: `SEQ`, `KEY`, `PATH`, `INDEX`,
`VALUE` and `THIS`. `path =>`, `outer => TRUE` and `mode => ARRAY | OBJECT | BOTH`
are honoured, `TABLE(FLATTEN(…))` works as well as the lateral form, and `VALUE`
is JSON, so `VALUE:x` and `VALUE::number` read through it.

`recursive => TRUE` is refused. It changes which rows come back, and a wrong row
count is exactly the failure this server exists to expose.

Three honest gaps: `SEQ` is the output row number rather than a stored sequence;
`PATH` is rebuilt from the element's key or index, so a document reached through a
path that was not given as `path =>` reports the local path, not the full one back
to the root; and the single row `outer => TRUE` keeps for input that cannot expand
comes back NULL in every column, where Snowflake repeats `THIS` (and numbers
`SEQ`) in that row.

### Named file formats are objects, and stages and formats can be described

`CREATE FILE FORMAT` used to read the name, throw the rest away, and report
success. `SHOW FILE FORMATS` therefore had nothing to list, and `DESCRIBE FILE
FORMAT` had nothing to describe. A format is now recorded with its `TYPE` (CSV if
none is given, as Snowflake defaults) and the options exactly as written, and the
three statements that report on it tell the truth:

```sql
create file format SNOWTEST.PUBLIC.JSON_F TYPE = JSON COMPRESSION = 'AUTO';
show file formats;
-- JSON_F | SNOWTEST | PUBLIC | JSON | SYSADMIN
describe file format SNOWTEST.PUBLIC.JSON_F;
-- type              | JSON
describe stage SNOWTEST.PUBLIC.S_DESC;
-- url | has_credentials | create_on | type | owner | comment | directory_enabled
```

`DESCRIBE STAGE` and `DESCRIBE FILE FORMAT` answer in Snowflake's property table
— `parent_property`, `property`, `property_type`, `property_value`,
`property_default` — rather than in the column list a table returns. A stage
reports `url`, `has_credentials`, `create_on`, `type`, `owner`, `comment` and
`directory_enabled`; a format reports `type`, every option it was created with,
then `owner` and `create_on`.

Three honest gaps, all on `/operations` too: `has_credentials` is always `FALSE`
because no stage credentials are stored, `directory_enabled` is always `FALSE`
because there are no directory tables, and a format's options are stored rather
than applied — `COPY INTO` still reads its own `FILE_FORMAT = (…)` list.
Formats are held in memory like roles and warehouses, so a restart forgets them; a
`DROP SCHEMA` or `DROP DATABASE` takes them with it.

`DESCRIBE SEQUENCE` is refused as a missing object rather than as unimplemented
syntax, which is what Snowflake would say about a sequence that does not exist.
Sequences themselves are still not implemented, `seq.NEXTVAL` included; that row
is `partial` on `/operations` and says so.

### Sequences

Sequences were the last "not implemented" row left in the Metadata tab: `SHOW
SEQUENCES` returned an empty shape, `seq.NEXTVAL` failed outright. DuckDB has
sequences of its own, so the work was the Snowflake surface around the counter,
not the counter itself:

- `CREATE [OR REPLACE] SEQUENCE [IF NOT EXISTS] [db.schema.]name [START [WITH] n]
  [INCREMENT [BY] n] [ORDER | NOORDER] [COMMENT '…']`, a negative increment
  included, and `DROP SEQUENCE [IF EXISTS]`
- `seq.NEXTVAL`, `NEXT VALUE FOR seq` and `seq.CURRVAL`, with the name resolved
  from the session when it is not qualified, so `SELECT MY_SEQ.NEXTVAL` and
  `INSERT … VALUES (NEXT VALUE FOR MY_SEQ)` both work
- `ALTER SEQUENCE … RESTART [WITH n]` and `… SET INCREMENT [BY] n`, which rewrite
  the definition rather than failing on DuckDB's missing ALTER: a bare `RESTART`
  returns to the sequence's own start value, and a `SET` keeps the value it would
  have handed out next
- `SHOW SEQUENCES` reports `next_value`, `interval` and `ordered` (always `YES`)
  from the live counter; `DESCRIBE SEQUENCE` answers with the row Snowflake
  returns for one
- a value is not rolled back with a failed transaction, which is Snowflake's rule
  too; `CURRVAL` is per session and errors before that session's first
  `NEXTVAL`, again as Snowflake does

Two limits, both stated on `/operations`: `ORDER`/`NOORDER` and `COMMENT` are
accepted and not stored, and any other option — `CACHE`, `RENAME TO` — is
refused rather than ignored.

### Defects found in review, fixed before the release

Three came out of probing this branch, and each changed what a client sees:

- `LATERAL FLATTEN(…) AS "f"` failed on a quoted alias. The alias is masked to an
  identifier placeholder before the translation looks for it, so an internal
  `AS FLATTEN_0` was inserted in front of the user's own alias and DuckDB refused
  the statement. Quoted aliases are recognised now, and no internal alias is
  added when one is given.
- A grant outlived the object it was made on: `DROP TABLE` left it answering in
  `SHOW GRANTS`. Grants are resolved to `DB.SCHEMA.NAME` when they are made, the
  way Snowflake resolves them — which also makes an unqualified `SHOW GRANTS ON
  TABLE t` and an unqualified `DROP TABLE t` agree with a qualified grant — and
  dropping a table, view, stage, file format, schema or database now takes its
  grants with it.
- `DESCRIBE STAGE` reported a fresh `create_on` on every call. A stage's creation
  time is kept with the definition and persisted in `stages.json`, so it survives
  a restart and does not move.

### Version and image tag

`package.json` and the `compose.yaml` fallback are `4.0.0`; `/operations` dates the
new rows to this release.

## Changes to existing surfaces

| Surface | Change |
|---|---|
| `GRANT` / `REVOKE` | Accepted and recorded, instead of failing with a DuckDB parser error |
| `SHOW GRANTS` | Answers from the recorded grants in all four variants, instead of returning no rows |
| `LATERAL FLATTEN`, `TABLE(FLATTEN(…))` | Translated to `json_each`; `GET`-style no-op before |
| `DROP ROLE` | Also drops the role's grants |
| `CREATE FILE FORMAT` | Recorded with its `TYPE` and options, instead of accepted and forgotten |
| `SHOW FILE FORMATS` | Lists the formats in scope, instead of returning no rows |
| `DESCRIBE STAGE`, `DESCRIBE FILE FORMAT` | Snowflake's five-column property table, instead of "Not implemented." |
| `DESCRIBE SEQUENCE` | Answers object-not-found, because sequences are not objects here |
| `DROP SCHEMA`, `DROP DATABASE` | Also drop the file formats inside them |
| `GET /operations` | `GRANT`/`REVOKE` and `SHOW GRANTS` rows; `FLATTEN` row; two `Not supported` entries reworded |
| Image tag | `snowtest:4.0.0`, read from `package.json` |

## Upgrading

```bash
./setup.py redeploy          # rebuilds as snowtest:4.0.0, keeps the data volume
# or by hand
podman build --layers=false --format docker -t snowtest:4.0.0 .
```

No configuration or schema change is needed.

## Known limitations

- Access control is recorded, never checked: no statement is authorised or
  refused, and `SHOW GRANTS` reports intent rather than effect.
- `FLATTEN ... recursive => TRUE` is refused.
- `FLATTEN` reports `SEQ` as a row number, and a local `PATH` unless `path =>`
  was given.
- `ALTER SCHEMA ... RENAME TO` and `... SWAP WITH` are unchanged: still refused.
- File formats live in memory like roles: a restart forgets them, and their
  options never reach `COPY INTO`, which reads its own `FILE_FORMAT = (…)`.
- `DESCRIBE SEQUENCE` reports every name as missing; sequences themselves are
  still unimplemented, `seq.NEXTVAL` included.
- Streams, tasks, dynamic tables, Snowpark, Snowpipe and ODBC are unchanged:
  still not supported.
