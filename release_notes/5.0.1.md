# snowtest 5.0.1 — Release Notes

**Release date:** 2026-11-18

No wire format, storage or configuration changed. 5.0.1 widens what the
fidelity pass admits to — constructs that ran and returned a different answer
from Snowflake's were being marked `verified` — and fixes five of those
differences outright, so some statements now return Snowflake's answer instead
of DuckDB's. `PARSE_JSON` on malformed input now fails where it used to return
NULL; see [What changes for existing setups](#what-changes-for-existing-setups).

## What changed

### More constructs are reported as approximate

5.0.0 reported three: variant paths, `FLATTEN` and `CONVERT_TIMEZONE`. Running
timezone queries against a live instance showed others that return a plausible
but wrong answer with no warning, which is exactly what the verdict exists to
catch. They are now reported, with the same `feature` / `detail` shape:

| Feature | Why it is approximate |
|---|---|
| `CURRENT_TIMESTAMP`, `LOCALTIMESTAMP`, `GETDATE` | DuckDB's clock ignores the session `TIMEZONE`; the offset is always UTC |
| `TIMESTAMP_LTZ`, `TIMESTAMP_TZ` (`::` and `CAST … AS`) | cast to `TIMESTAMPTZ` with no session zone; the offset is always UTC |
| `TO_TIMESTAMP_LTZ`, `TO_TIMESTAMP_TZ` and their `TRY_` forms | same, and `TO_TIMESTAMP_LTZ` lands on a plain `TIMESTAMP` |
| `TYPEOF` | DuckDB's `typeof()` names DuckDB types (`JSON`), not Snowflake's variant types |
| `DATEADD`, `DATE_ADD`, `TIMESTAMPADD` | `DATE + INTERVAL` returns a `TIMESTAMP` where Snowflake returns a `DATE` |
| `TO_VARCHAR`, `TO_CHAR`, `TO_TEXT` (one argument, timestamp input) | `CAST … AS VARCHAR` gives `2026-01-15 12:00:00`; Snowflake's default output format gives `2026-01-15 12:00:00.000` |
| `HASH` | DuckDB's `hash()` produces different values from Snowflake's |
| `ARRAY_CONSTRUCT` with a `NULL` element | DuckDB keeps `NULL`; Snowflake stores `undefined` |

Each occurrence is reported once, as before. The clock is counted before its
rewrite, because the rewrite emits `CURRENT_TIMESTAMP` again.

Still not reported, because they translate exactly: `TIMESTAMP_NTZ`,
`TO_TIMESTAMP_NTZ`, `SYSDATE` and `CURRENT_DATE`.

### Where each one stops

- **Casts.** `AS TIMESTAMP_TZ` counts only as the tail of a `[TRY_]CAST(…)`. A
  column alias named `timestamp_tz` is not a cast and is not reported, so
  `strict` does not refuse it.
- **`DATEADD`.** Reported only when the operand is visibly a `DATE` —
  `::DATE`, `CAST(… AS DATE)`, `DATE '…'`, `CURRENT_DATE`, or `TO_DATE(…)` —
  and the unit is day or larger. A `DATE` column cannot be told from a
  timestamp at translation time, and warning on every `DATEADD` would be the
  noise the report is built to avoid. An hour or smaller unit returns a
  timestamp in Snowflake too, so it is not reported.
- **String literals and quoted identifiers** are masked before any of this
  runs, so `'x::timestamp_ltz'` is not a cast.
- **One registry.** Every reportable construct name and its detail now lives in
  `src/sql/approximations.ts`; `dialect.ts` reports by name and an unlisted
  name throws, so a typo cannot reach `QUERY_HISTORY` or `MODEL_FIDELITY`.
  Names are unchanged.
- **`TO_VARCHAR`.** The same visible-operand rule as `DATEADD`: a cast to a
  timestamp type, a `TIMESTAMP '…'` literal, the clock, or `TO_TIMESTAMP*(…)`.
  With a format argument the format is translated and nothing is reported.
- **`HASH`** is reported on every call; `HASH_AGG` is not.
- **`ARRAY_CONSTRUCT`** is reported only when an element is the literal `NULL`.

### Five differences fixed instead of reported

Where Snowflake's answer is cheap to reproduce exactly, snowtest now gives it,
and the construct stays unreported because nothing is approximated any more.
Each was confirmed against a running instance before the change.

| Construct | Before | Now (as Snowflake) |
|---|---|---|
| `ORDER BY x DESC` with NULLs | NULL sorted last | NULL sorted first; ascending still sorts it last |
| `GREATEST` / `LEAST` | `greatest(1, NULL, 3)` → `3` | `NULL` when any argument is NULL |
| `OBJECT_CONSTRUCT` | `{"b":2,"z":null,"a":1}` | `{"a":1,"b":2}`: SQL-NULL key or value dropped, keys sorted (uppercase first); a JSON `null` value is kept |
| `PARSE_JSON` | malformed input → `NULL` | malformed input fails; blank input still → `NULL` |
| `DATEDIFF(week, …)` | whole 7-day spans: Sunday → Monday is `0` | Monday boundaries crossed: Sunday → Monday is `1` |

How each is done:

- **NULL order** is one DuckDB setting, `default_null_order =
  nulls_last_on_asc_first_on_desc`, applied to the instance, so it holds for
  `ORDER BY` and window `ORDER BY` alike. The case it matters for is
  `QUALIFY ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) = 1`,
  which now keeps the row Snowflake keeps.
- **`GREATEST` / `LEAST`** become a `list_reduce` over the arguments that
  returns NULL as soon as it meets one. Each argument is evaluated once, so
  `GREATEST(seq.nextval, 0)` draws one value, not two, and nested calls grow
  linearly.
- **`OBJECT_CONSTRUCT`** builds a map from the pairs, filtered and sorted, and
  casts it to JSON. `OBJECT_CONSTRUCT()` gives `{}`; `OBJECT_CONSTRUCT(*)` is
  translated as before.
- **`PARSE_JSON`** is a strict cast; malformed input fails with Snowflake's
  `100069 (22P02) Error parsing JSON`. `TRY_PARSE_JSON` is new and keeps the old
  lenient behaviour.
- **`DATEDIFF(week, …)`** truncates both sides to the week first. Snowflake's
  weeks start on Monday under the default `WEEK_START` of 0. Day, month,
  quarter and hour already counted boundaries as Snowflake does.

### One known gap, neither reported nor fixed

Integer division returns a double: `1/3` is `0.3333333333333333` where
Snowflake returns `0.333333`. It is an operator, not a function call, so there
is no rewrite to hang a report on, and reporting every `/` would bury the
warnings that matter. The README lists it.

## What changes for existing setups

- **`strict` refuses more.** A dbt model using `CURRENT_TIMESTAMP` — including
  dbt-snowflake's `current_timestamp()` macro, which wraps it in
  `convert_timezone('UTC', …)` — or an LTZ/TZ cast is now refused under
  `strict`. Under `report`, the default, nothing is refused; those statements
  now read `approximate` instead of `verified`.
- **Verdicts can name more constructs.** `CONVERT_TIMEZONE('UTC',
  CURRENT_TIMESTAMP)` now reads `approximate: CURRENT_TIMESTAMP,
  CONVERT_TIMEZONE`. Rows already in `QUERY_HISTORY` and `MODEL_FIDELITY` keep
  the verdict they were written with.
- **`PARSE_JSON` fails on malformed JSON.** A model or seed that relied on bad
  input quietly becoming NULL now errors, as it would in Snowflake. Switch it
  to `TRY_PARSE_JSON` where NULL is the intent.
- **Descending sorts put NULLs first.** A test that expected NULLs at the end
  of an `ORDER BY … DESC` was asserting DuckDB's order, not Snowflake's; add
  `NULLS LAST` if that is what it needs.
- **`GREATEST`, `LEAST`, `OBJECT_CONSTRUCT` and week `DATEDIFF` results can
  change** where NULLs or week boundaries are involved, to Snowflake's values.
- **`compose.yaml`** defaults the image tag to `5.0.1`.
