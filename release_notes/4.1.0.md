# snowtest 4.1.0 — Release Notes

**Release date:** 2026-11-15

A small feature release: the server now keeps a record of every statement it ran
and how long it took, where Snowflake keeps it, so the answer to "how slow was
that query" is a `select` rather than a log line. Nothing in the wire protocol,
the SQL surface or the storage layout of your databases changed.

## What changed

### Query timings are a table

Each statement is noted in `SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY`, the name a
real account uses:

```sql
select query_text, total_elapsed_time, rows_produced, execution_status
from snowflake.account_usage.query_history
order by query_id desc limit 20;
```

- `query_id`, `query_text` (trimmed to 200 characters), `query_type` (the leading
  verb), `database_name`, `schema_name`, `session_id`, `user_name`, `role_name`,
  `warehouse_name`, `warehouse_size`
- `start_time`, `end_time`, `total_elapsed_time` in milliseconds, `rows_produced`
- `execution_status` (`SUCCESS` or `FAIL`), with `error_code` and `error_message`
  holding exactly what the client was told

Failed statements are recorded too — that is usually the interesting row. The
timing window closes before the row is written, so a statement never pays for its
own bookkeeping, and a statement that reads the table does not see itself.

### Emptying it is a decision, not a policy

Nothing prunes this table. Nowhere in the server is there a delete, a cap or a
clock: rows stay until someone empties them, which is the point of a stub you
keep around for a week of tests.

The landing page has a **Clear Data** tab for that:

- **Clear timings** empties the table and nothing else, behind a two-step
  confirmation.
- **Everything** drops databases and their files, stages, sessions, statement
  handles and the timings table, then rebuilds the configured catalog. Its button
  stays disabled until you type `Delete All Data` exactly — spaces, capitals and
  all. The phrase is matched in the page; `POST /_snowtest/reset` itself still
  resets when called directly, as it always did.

`POST /_snowtest/queries/clear` is the same action for a script, and answers
`{"cleared": <rows>}`.

### What is deliberately missing

The table has the columns a stub can fill and not the ones it cannot.
`bytes_scanned`, `bytes_written`, `credits_used_cloud_services` and the queue
timings are absent rather than guessed: this server does not size warehouses, so
it has no honest way to bill you. `total_elapsed_time` is wall clock around the
statement, not Snowflake's compile/execute split.

### `setup.py`: `up` and `down` are just up and down

`up` used to build, seed and replace things depending on the flags it was given,
and `down` removed the container rather than stopping it. Both are now the simple
pair the names promise:

- `up` starts the container, creating it only when it does not exist, and waits
  until it is healthy. It never builds, replaces or clears anything.

The one thing `up` still writes is the example data, and only once: the example
tables from `data/examples.sql` are loaded when `up` has *just created* the
container, so a first install has something to query — the `EXAMPLES` schema the
quick start and the dbt examples assume. A container that already exists is never
seeded, started-from-stopped included, because seeding replaces those tables and
`up` has no business rewriting a test's data. Skipping it entirely is
`redeploy --no-seed-examples`.
- `down` stops the container. It removes nothing — not the container, not the
  `<name>-data` volume, not the stage files.

Everything that changes the deployment moved to `redeploy`, which keeps its
options and gains the two switches that used to live on `up`. Both default on, so
`./setup.py redeploy` still means "pick up my code change":

| Flag | Default | Effect when switched off |
|---|---|---|
| `--recreate / --no-recreate` | on | `--no-recreate` keeps the container that is there |
| `--rebuild / --no-rebuild` | on | `--no-rebuild` keeps the image already tagged |

`--no-cache`, `--keep-stages`, `--no-seed-examples`, `--write-profile` and the
common flags are unchanged. `reset` is still the one command that drops data.

## Upgrading

No configuration, schema or client changes. The history lives in its own file
under `SNOWTEST_DATA_DIR` (`query_history.db`) and is not restored as a user
database; with no data directory it is in memory, like everything else. Rolling
back to 4.0.0 leaves the file unread, which is harmless.
