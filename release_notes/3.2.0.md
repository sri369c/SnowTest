# snowtest 3.2.0 — Release Notes

**Release date:** 2026-11-14

A minor release, because one default moved: the container is now published on
`127.0.0.1` instead of every interface. The SQL engine, protocol and storage are
unchanged; what changed is how the container is deployed, how you find out where
it went, and what it leaves behind on disk.

## What changed

### The container is published on loopback by default

`setup.py up`, `setup.py redeploy` and `compose.yaml` now publish
`127.0.0.1:3030:3030` rather than `3030:3030`. `/_snowtest/*` is an
unauthenticated control plane — anything on the network could reset the catalog
or rewrite the stage — so exposing it was the wrong default.

Reaching it from another host is still possible, deliberately:

```bash
./setup.py up --bind 0.0.0.0
```

The summary and `setup.py status` both print what was actually published.

### `status` answers "is it deployed, and where?"

`./setup.py status` used to print two lines. It now prints the engine, the podman
machine behind it, the store it is using (rootful or rootless, with its graph
root), whether the container exists, the published ports, the machine's Windows
named pipe, and the health endpoint.

Two of those exist because one mistake keeps recurring:

- **The store.** One podman machine holds a rootful and a rootless store, with
  separate containers, volumes and images. A deploy can land in one while the
  shell reads the other.
- **The pipe.** A healthy container with a missing `\\.\pipe\<machine>` is exactly
  the state where the CLI works and Podman Desktop shows an empty window. That
  combination makes `status` exit `1` and say which command fixes it.

`status` also warns when a running container is on an older image than its tag,
which is otherwise invisible: rebuilding a tag does not touch a running container.

### `up` starts a stopped container instead of recreating it

A machine restart leaves the container stopped, not gone. `up` now starts it in
place, keeping its identity, instead of removing and recreating it with the flags
it happens to have been given. `--recreate` still forces the old behaviour, and
`redeploy` is still what picks up changed flags or a new image.

### Podman builds keep no `<none>` images

`podman build` now runs with `--layers=false --format docker`, followed by
`image prune -f`. The first flag stops intermediate cache images being created at
all; prune cannot remove them afterwards, because they are ancestors of the
tagged image. The second records the Dockerfile's `HEALTHCHECK`, which podman's
OCI default silently drops.

`setup.py` now fails the build if the result leaves any dangling image, rather
than leaving it to be discovered later.

### The image tag follows `package.json`

`setup.py` reads the version once and derives `snowtest:<version>` from it.
`compose.yaml` cannot, so it takes `${SNOWTEST_VERSION:-3.2.0}`. A release bump
is one number in `package.json` plus that one fallback.

### Smaller changes

- `.dockerignore` excludes `.snowtest`, `.env`, `.pytest_cache` and `.coverage`,
  so stage files and local settings stay out of the build context.
- `setup.py down` says in its output that the data volume and stage directory are
  kept. It never deletes either.
- The README and the server's own usage page document `status`, `--bind` and the
  machine-restart behaviour.

## Changes to existing surfaces

| Surface | Change |
|---|---|
| `setup.py up`, `redeploy`, `compose.yaml` | Published on `127.0.0.1` unless `--bind` widens it |
| `setup.py status` | Prints engine, store, machine, pipe, ports and health; exits `1` when the container answers but the Windows pipe is missing |
| `setup.py up` | Starts an existing stopped container in place; `--recreate` replaces it |
| `setup.py up --bind` | New flag, default `127.0.0.1` |
| `setup.py` image tag | Read from `package.json` instead of hard-coded |
| podman build | `--layers=false --format docker`, then `image prune -f`, then a dangling-image check |

## Upgrading

```bash
./setup.py redeploy          # rebuilds as snowtest:3.2.0, keeps the data volume
# or by hand
podman build --layers=false --format docker -t snowtest:3.2.0 .
```

No configuration or schema changes are needed. If you reached the container from
another machine, add `--bind 0.0.0.0` to keep doing so.

## Known limitations

- The Windows pipe check only runs on Windows and only for podman; a docker
  engine has no machine and no pipe to inspect.
- `compose.yaml`'s version fallback has to be bumped by hand.
- Stage directories are still host paths, so a host-side client cannot reach a
  stage that lives inside a container volume.
